# VB 투구 사건 보정 설계 (설계만, 구현·적용 안 함)

근거는 캡처 대조 8경기(`README.md` "캡처 기반 사례 대조 기록", `results/case*_correspondence.csv`), TrackMan, VB 원본 JSON이다. 이 문서는 원본·curated·공개 값을 바꾸지 않는다. 아래 모든 적용 단계는 별도 승인 사항이다.

## 1. 확인된 오류 유형

| 유형 | 증상 | 틀리는 필드 | 대체로 믿을 수 있는 필드 | 사례 |
|---|---|---|---|---|
| A. 타석 분리·궤적 복제 | 투구 외 사건(대주자, 마운드 방문, 투수 교체, 투수판 이탈) 자리에서 새 타석이 열림. 새 타석 첫 1–2행이 앞 공의 궤적 9계수를 그대로 가짐 | 새 타석 첫 행들의 궤적·`px/pz`, 카운트(0-0 재시작), 앞 타석 결과(빈값) | 호출, 표시 구속 | 김택연–임지열, 서건창, 최주환 |
| B. 구속·구종 표시 밀림 | 구속 0 선행 기록에서 시작해 표시 구속·구종이 한 공씩 늦게 붙다가, 같은 공의 두 번째 기록에서 제자리로 돌아옴 | 밀린 구간의 구속·구종 | 호출, 궤적 | 정수빈, 박해민(3회), 조수행 |
| C. 같은 값 중복·타석 복제 | 한 공(또는 한 타석)이 값이 완전히 같은 행으로 두 번 기록됨. 첫 기록은 아웃 수 등이 덜 반영되기도 함 | 행 수, 카운트, 아웃 수 | 두 행 중 뒤 기록의 값 | 허경민, 이형종, 채은성, 김휘집 등 |
| D. 공 누락·결과 누락 | 타석 앞쪽 공이 빠짐(뒤쪽 복제와 함께 나오는 경우가 많음). 결과가 빈값 | 투구 수, 카운트, 결과 | 남은 행의 호출·구속 | 김건희, 노진혁, 양의지, 이주형, 허경민(볼넷 결과) |
| E. 호출 오류 | 볼이 T나 X로, 스트라이크가 X로 기록됨. 구속·구종도 틀림 | 호출, 구속, 구종 | (행 위치 정도) | 힐리, 오재일 |
| F. 경기 구간 누락 | 여러 반이닝의 타석이 통째로 빠지고 블록 순서가 뒤섞임 | 해당 구간 전체 | 없음 | 2021-05-12, 2021-06-06 외 2경기 |

네이버 목록(문자 중계)도 A·B·C·D를 VB와 같은 모양으로 보인다. 같은 상위 기록을 받는 것으로 보인다(추정). 네이버 그림은 C의 중복을 거르지만, D의 누락은 그림에도 남는다.

## 2. 자동 탐지 규칙 (검토 대기 목록을 만드는 용도, 자동 보정 아님)

| 규칙 | 잡는 유형 | 데이터 | 현재 규모 |
|---|---|---|---|
| R1. 같은 경기에서 서로 다른 행의 궤적 9계수가 완전히 같음(DUP_TRAJ) | A, B, C | VB | 검토 목록 29타석 중 대부분 |
| R2. 같은 반이닝에서 같은 타자의 타석이 연속(SPLIT_SAME / SPLIT_PCHANGE) | A, C | VB | 검토 목록에 포함 |

| R4. 표시 구속과 궤적 계산 구속의 차이 > 8km/h (`speed_consistency.py`) | B, E, A | VB | 2023–2026 시즌당 14–73행. 2019–2022는 평소 오차가 커서(p99 4–8km/h) 기준을 따로 정해야 함 |
| R5. 첫 행 구속 0 | B, A | VB | 사례 4에서 5회 |
| R6. 반이닝별 VB 투구 수 < TrackMan(`game_gap_scan.py`) | F, D | TrackMan(2019–2024, KIA 홈 제외) | 경기 단위 4경기 |
| R7. 같은 공의 TrackMan 카운트 전이와 VB 호출 불일치(PR #29 카운트 불일치 시작점) | E | TrackMan | 2024 시작점 666구(대부분 B→TM 스트라이크) |
| R8. 네이버 목록 카운트 연속성 깨짐(표시 카운트가 이전 카운트와 이어지지 않음) | D, C | 네이버 | 도입 후 |

오탐 점검:

- R1·R2는 실제 야구에서 사실상 생길 수 없다. 오탐보다 **원인 해석**(A인지 C인지)이 문제다.
- R4는 시즌별 중앙 오프셋을 먼저 빼고, 확인된 사례로 기준을 조정한다.
- R6은 TrackMan 경기 매핑이 틀린 경우 오탐이 된다. 매핑이 일대일인 경기만 쓴다.
- **E(호출 오류)는 흐름이 우연히 성립하면 R3에 걸리지 않는다.** TrackMan(R7)이나 네이버(R8)가 없는 2025–2026에서는 대부분 놓친다. 검토 목록은 전수 목록이 아니다.

## 3. 필드별 근거 우선순위

| 필드 | 1순위 | 2순위 | 3순위 | 비고 |
|---|---|---|---|---|
| 투구 순서·수, 호출, 카운트, 타석 결과 | 영상(사용자 확인) | 네이버 목록의 카운트 연속성 | TrackMan 카운트 전이(2019–2024) | 네이버 목록 자체의 중복·누락은 카운트로 거른다 |
| 구속·구종 | TrackMan(2019–2024, 9절) | 궤적 계산 구속(VB·네이버 궤적 계수) | 표시 구속(VB `spd`, 네이버 `speed`) | 2019–2023 표시 구속은 연결 조건으로 쓰지 않는다(9절). B 유형은 표시값을 믿지 않는다 |
| 위치·궤적 | 네이버 PTS 투구 단위 기록(검증 후, 4절) | 복제되지 않은 VB 궤적 | 없음 → **null** | TrackMan 원자료에는 탄착 위치 컬럼이 없다 |
| 투수 | VB `pitcherId`와 네이버 교체 문구 | TrackMan | — | 투수 교체로 나뉜 타석은 투수 구분은 맞다 |

**위치를 어디서도 얻을 수 없는 공이 남는다.** 네이버 그림에도 없는 누락 공(D), 구간 누락(F), 궤적이 복제된 행 중 원본을 가릴 수 없는 행(A)이 그렇다. 이 공들은 사건 흐름(카운트·상태)에만 쓴다. 위치 기반 학습·채점에서는 제외한다. 좌표를 추정해 채우지 않는다.

## 4. 네이버 API에서 위치를 가져오는 계획

### 먼저 확인할 것 (검증 전에는 설계를 확정하지 않음)

1. 경기 중계 API(`/schedule/games/{id}/relay?inning=N`) 응답에 투구 단위 추적 기록이 있는지. 필드 이름, 좌표 단위, 기준면, 궤적 계수 포함 여부를 확인한다. 현재 `naver.py`는 `textOptions`의 `ptsPitchId`, 폭투·포일 문구, 선발 포수만 쓴다. 추적 기록 필드는 이 저장소에서 한 번도 저장·확인된 적이 없다.
2. 네이버 좌표가 **VB 궤적과 같은 값인지.** 같은 상위 공급원이라면 네이버 위치는 독립 검증 근거가 아니다. 다만 투구 ID 단위로 중복이 걸러져 있으므로 **A·B·C의 재귀속에는 쓸 수 있다**. 값이 다르다면 어느 쪽이 ABS 호출과 맞는지부터 따로 본다.
3. 투구 ID(`ptsPitchId`)가 중복 기록(C)과 선행 기록(B)을 하나로 묶는지. 네이버 그림이 중복을 거르는 이유가 이것인지 확인한다.

### 실행 위치와 범위

- 이 환경(클라우드 세션)에서는 네이버가 차단돼 있다. 수집은 **GitHub Actions 수동 실행**이나 사용자 로컬에서 한다. 기존 `NaverRelayClient`와 같은 경로다.
- 원본 응답은 `data/raw/naver/`(이미 gitignore)에 저장한다. 커밋하지 않는다. 분석에는 투구 단위로 정규화한 표만 쓴다.
- 범위는 단계적으로 넓힌다. 먼저 검토 대기 경기 8개 + R6 추가 2경기에서 1·2·3번 질문에 답한다. 결과를 보고 R1·R4 신호가 있는 경기로 넓힐지 정한다. 전 경기(시즌당 약 720경기 × 약 10이닝 요청)는 검증 결과가 좋을 때만 검토한다.

### TrackMan 대조로 채우는 방식

- 반이닝 안에서 (투수, 타자) 순서로 네이버 투구 ID 목록과 TrackMan 투구를 정렬한다. 카운트는 연결 조건이 아니라 대조값으로 쓴다(PR #29 규칙과 동일).
- TrackMan은 **순서·수·카운트·구속·구종**을 확인하고, 네이버는 **투구 ID와 위치**를 준다. 둘 다 없는 필드는 null로 둔다.
- 두 자료가 어긋나면 자동으로 고르지 않는다. 사람 확인(캡처·영상) 대기로 보낸다.

## 5. 보정표 형식 (제안)

`data/corrections/vb_pitch_corrections.json`. 원본 JSON은 그대로 두고, 파서가 타석 조립 직전에 적용한다. curated 행에는 `correction_id`와 `field_sources`가 남는다.

```json
{
  "schema_version": 1,
  "games": {
    "20250809OBWO0": {
      "raw_sha256": "<원본 JSON sha256, 다르면 적용 중단>",
      "plate_appearances": [
        {
          "id": "2025-0809-OBWO-9b-lim",
          "source_rows": [[17, 2, 0], [17, 3, 0], [17, 3, 1], [17, 3, 2], [17, 3, 3], [17, 3, 4], [17, 3, 5], [17, 3, 6], [17, 3, 7]],
          "action": "merge_pa",
          "result": {"text": "유병", "outs_after": 3, "evidence": "naver_relay"},
          "pitches": [
            {"n": 1, "call": "B", "speed_kmh": 134, "type": "슬라이더", "row": [17, 2, 0], "location": "row", "evidence": ["naver", "video"]},
            {"n": 2, "call": "B", "speed_kmh": 137, "type": "슬라이더", "row": [17, 3, 0], "location": null, "evidence": ["naver", "video"], "note": "궤적이 1구 복제"},
            {"n": 5, "call": "S", "speed_kmh": 151, "type": "직구", "row_candidates": [[17, 3, 3], [17, 3, 4]], "location": null, "note": "중복 후보, 좌표 미확정"}
          ],
          "excluded_rows": [[17, 3, 4]],
          "reviewed_by": "user", "reviewed_at": "2026-09-27", "urls": ["https://m.sports.naver.com/game/20250809OBWO02025/relay"]
        }
      ]
    }
  }
}
```

- `source_rows`는 원본의 (반이닝 블록, 타석, 투구) 인덱스다. 행을 지우지 않고, 쓰지 않는 행은 `excluded_rows`로 표시한다. 기존 `parse_status`가 `ok`가 아니면 `swing_take._eligible`이 제외하는 경로를 쓴다.
- 필드마다 근거를 남긴다(`evidence`). `location: null`은 "위치 모름"이지 0이 아니다.
- 누락 공은 `row: null`로 추가할 수 있다. 호출·카운트는 흐름에 쓰고, 위치 기반 모델에서는 제외한다.

## 6. 작업 흐름

1. **탐지**: R1–R7로 검토 대기 목록을 만든다(경기·타석·규칙).
2. **가져오기**: 목록의 경기만 네이버 중계 원본을 수집한다(4절, CI 또는 로컬).
3. **자동 제안**: 네이버 투구 ID·TrackMan·VB 행을 정렬해 대응안을 만든다(확정 / 복수 후보 / 불명).
4. **사람 확인**: 제안과 자료가 어긋나는 공만 사용자에게 캡처·영상 확인을 요청한다(현재 방식).
5. **보정표 작성**: 확인된 타석만 5절 형식으로 기록한다.
6. **검증**: 보정 뒤 해당 타석의 흐름 플래그 0, 투구 수·결과·아웃이 근거와 일치하는지 확인한다. 보정 대상 밖 행의 `pitch_sha256`은 바뀌지 않아야 한다.

## 7. SBJ 반영 선택지 (모두 승인 필요)

- 보정표 적용 여부와 적용 시점(시즌 단위, 한 번에)
- 위치 null 행을 `p_zone` 목표와 위치 특성에서 제외하고, 카운트·상태 흐름에는 포함할지
- E 유형처럼 호출이 고쳐진 공을 학습·채점에 다시 넣을지
- 재학습 변동(3절 보류 실험: 무관 9행 제외만으로 전 선수 평균 0.08–0.32점)을 줄이는 모델 안정화를 보정과 함께 할지
- 공개 SBJ 값 변경 공지 방식

## 8. 남은 불확실성

- 네이버 API의 추적 기록 필드(4절 1–3번)는 PR #31에서 10경기로 확인했다. `ptsOptions`에 수평 위치·존 높이·궤적 계수가 있고, 확정 대응 82쌍 중 76쌍이 VB 수평 위치와 0.01ft 이내로 같았다. 같은 공급원일 수 있으므로 독립 검증은 아니다. 좌표 단위·기준면은 응답 수치에 근거한 추정이다.
- A–F 유형은 8경기에서 얻은 것이다. 빈도와 다른 유형의 존재는 모른다.
- "뒤 기록의 구속이 맞다"(B)는 TrackMan으로 3건 확인했을 뿐이다.
- 2025–2026은 TrackMan이 없어 E·F 탐지가 약하다.

## 9. TrackMan 기준 대조 하네스 (2019–2024)

2019–2024는 TrackMan을 **순서·개수·구속·구종의 기준 원자료**로 두고, VB와 네이버의 각 필드를 여기에 맞춰 검사한다. 위치는 TrackMan에 없으므로(`trackman_history.csv`에 탄착 위치 컬럼 없음) 이 하네스는 "이 궤적이 그 순번의 공이 맞는가"까지 확인한다. 탄착 위치 자체를 검증하지는 않는다.

### 9.1 근거: 표시 구속은 기준이 될 수 없다

- VB 표시 구속과 궤적으로 계산한 구속의 차이, 상위 1% 절댓값(`results/speed_consistency.json`): 2019 7.7, 2020 6.2, 2021 5.1, 2022 4.2, 2023 3.2, 2024 0.5km/h. 2025는 중앙값이 +1.5km/h 이동했다. 구장별 측정기를 쓰다가 출처가 일원화됐다는 설명과 맞지만, 이 자료만으로는 일원화 시점을 정할 수 없다(추정).
- 네이버 조회 378구(PR #31, 2020–2021 구간 누락 4경기)에서 네이버 궤적 계수로 계산한 50ft 구속은, 경기별 중앙 오프셋(−0.6~−2.7km/h)을 빼면 TrackMan `rel_speed`와의 차이가 전부 3km/h 이내였다(상위 1% 0.5–0.8km/h).
- 같은 378구 중 네이버 **표시** 구속이 TrackMan과 ±3km/h 이상 어긋난 8구는, 궤적 구속으로는 모두 TrackMan과 맞았다. 같은 타석의 앞뒤 공과 카운트 전이도 맞았다. 어긋난 것은 표시 숫자뿐이다.
- 한 경기 전체가 일정하게 어긋나는 경우가 있다(20210512SSKT0, 네이버 표시−TrackMan 중앙값 −2.6km/h). 원인이 TrackMan 보정인지 표시 구속인지는 가르지 못했다. 그래서 오프셋은 시즌 단위가 아니라 **경기 단위**로 뺀다.

### 9.2 검사 항목

TrackMan 경기 매핑이 일대일인 경기만 쓰고, 양 팀 모두 1군 코드인 투구만 쓴다(PR #29 규칙). 각 검사는 검토 대기 목록을 만들 뿐, 자동으로 보정하지 않는다.

| 검사 | 비교 | 판정 기준 | 잡는 유형 |
|---|---|---|---|
| H1. 반이닝 투구 수 | VB·네이버 투구 수 vs TrackMan | 부족하면 대기 목록(R6) | D, F |
| H2. 타석 안 순번 정렬 | (투수, 타자) 타석 안에서 `pitch_of_pa` 순서 | 개수가 다르면 정렬하지 않고 대기 | A, C, D |
| H3. 궤적 구속 | 행의 궤적 계산 구속 vs 정렬된 TrackMan `rel_speed` | 경기별 중앙 오프셋을 뺀 잔차가 3km/h 초과 | A(복제 궤적), B(밀린 궤적) |
| H4. 표시 구속 | 표시 구속 vs TrackMan | 2024만 판정. 2019–2023은 기록만 한다 | B(표시 밀림) |
| H5. 구종 | 표시 구종 vs TrackMan `tagged_pitch_type` | 불일치는 기록만 한다(TrackMan 태깅도 오류가 있음) | B |
| H6. 카운트 전이 | VB 호출로 만든 다음 카운트 vs TrackMan 다음 공의 `balls_before`/`strikes_before` | 대조값. 연결 조건으로 쓰지 않는다(R7) | E |

- H3이 이 하네스의 핵심이다. 궤적 9계수 중복(R1)은 복제를 찾아도 어느 행이 원본인지 가르지 못했는데(사례 1, 김택연–임지열), H3은 각 행의 궤적 구속이 **어느 순번의 TrackMan 공과 맞는지**를 보여 준다. 두 공의 구속 차이가 3km/h 이하이면 H3도 가르지 못한다. 그때는 미확정으로 둔다.
- 네이버 궤적도 같은 H3을 통과한 것만 위치 후보로 쓴다. 통과해도 "그 순번의 공이다"라는 근거일 뿐, 위치가 독립적으로 검증된 것은 아니다.

### 9.3 TrackMan의 한계

- 2025–2026에는 TrackMan이 없다. 이 시즌은 H1–H6을 쓸 수 없고, R1–R5·R8만 쓴다.
- KIA 홈 경기는 2019–2024 전체가 TrackMan에 없다. 2024년 경기 미연결 26,388구 중 22,457구가 이 경우다.
- TrackMan에도 누락, 구종 태깅 오류, 경기 매핑 오류가 있을 수 있다. 호출(볼/스트라이크) 컬럼은 없고, 카운트 전이로만 간접 확인한다.
- 위치·호출 필드에서 TrackMan과 VB가 어긋나면 자동으로 고르지 않고 사람 확인(캡처·영상) 대기로 보낸다.

### 9.4 구현 순서 (제안, 읽기 전용 분석부터)

1. `speed_consistency.py`를 경기 단위 오프셋으로 확장하고, VB 궤적 구속과 TrackMan을 연결한 투구에서 H3 잔차 분포를 시즌별로 낸다. 확인된 사례(사례 1–8)가 걸리는지 먼저 본다.
2. H1·H2·H3을 하나의 경기 단위 대조 표(`results/trackman_harness_<season>.csv`)로 묶는다. 대기 목록 규모를 보고 기준을 조정한다.
3. 네이버 조회표(`naver_pitch_lookup.csv`)에 궤적 구속 열과 H3 판정을 추가한다.
4. 보정표 적용은 5–7절대로 별도 승인 뒤에 한다.
